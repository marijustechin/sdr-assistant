# Frontend audit — 2026-11-14

**Type:** read-only audit. No application code was changed.
**Scope:** `apps/web` (Next.js 16.4.3 / React 19 / Tailwind 4).
**Baseline:** `main` @ `f822d85` ("Document handover and maintenance plan"), `apps/web` = 29
source files, 1466 lines.
**Language:** requested in Lithuanian; written in English to match `HANDOVER.md`,
`AGENTS.md`, `README.md` and `TODO.md`.

Method: static reading of every file under `apps/web` plus the relevant API
controllers/DTOs/schema, and two reproduction commands (see §1.7). No API, database,
dev server or browser was started.

---

## 0. Summary

The new research flow (`entities/research` + `_pages/research` + `_pages/researches` +
`app/api/research/[jobId]`) is the canonical one, but it is a **prototype**: it displays a
status string and nothing else. The research **result, error and country/product context
are never rendered**, and polling has **no terminal-failure path**. The old-looking
`products/[id]` research form is **not dead code** — it is the only way to create a run,
so it cannot simply be deleted.

The layer split is already ~70% FSD (`_pages`, `entities`, `lib`). What is missing is
`shared/`, `features/`, contract schemas, and a rule that keeps route folders thin, so
"Lite FSD" is a good fit — with one addition that matters more than folder names: a single
shared source of truth for the API contract (see §4).

### 1.2 Which research flow is canonical?

**Canonical (new, single entry point):**

`products/[id]` (form) → `app/products/[id]/actions.ts:34` `POST /research` →
`redirect('/researches/{jobId}')` (`:71`) → `_pages/research` renders → `ResearchProgres`
polls `/api/research/{jobId}` → route handler proxies `GET /research/{jobId}`.

There is **exactly one** call that creates a research (`POST /research` appears once in
`apps/web`). `GET /research` (list) and `GET /research/:jobId` each have exactly one web
consumer.

**Not canonical, but not dead either:**

- `app/products/[id]/research-form.tsx` — looks like the "old form" (hand-written CSS
  classes, hidden inputs), but it is the **only** way to start a research run. Deleting it
  without a replacement removes the feature.
- `_pages/research` + `_pages/researches` — canonical, but prototype-grade: bare `<main>`,
  `<h1>`, `<p>`, no `.card`/`.page-header`/`.muted`, no links back, no result/error UI.

**Actually duplicated (not old-vs-new):**

- Two data-access styles: `entities/*/api` (research) vs `lib/products.ts` + inline
  `fetch` inside `app/products/page.tsx:24-42` (products).
- `Product` type declared twice: `lib/products.ts:3-9` and
  `app/products/page.tsx:12-18`.
- Product validation rules (name ≤ 200, description ≤ 2000) written twice:
  `app/products/actions.ts:25-37` and `app/products/[id]/edit/actions.ts:26-37`.
- Status rendered twice on the same page: `_pages/research/ui/research-page.tsx:16` and
  `_pages/research/ui/research-progress.tsx:82` — the first one goes stale (§2.2).

**Verdict:** nothing is obsolete at the routing level. The obsolete parts are the
parallel access layers and the two unvalidated ad-hoc fetch paths, not a route or form.

### 1.3 Polling state coverage

Implementation: `_pages/research/ui/research-progress.tsx:18-65`.

| State | Supported | Evidence / behaviour |
| --- | --- | --- |
| `QUEUED` | yes | polls at a fixed 2000 ms (`:52`); no queue position/ETA |
| `RUNNING` | yes | shows `stage` (`:83`) — raw implementation text, e.g. `First discovery step...` |
| `COMPLETED` | stops polling | `keepPolling=false` (`:43-44`); **result never rendered**, spinner frame freezes, no `router.refresh()` |
| `FAILED` | stops polling | **`error` never rendered**; no "try again" action |
| `INTERRUPTED` | type only | in `researchStatusSchema` (`model/types.ts:3-9`) but never assigned by the API; the UI would treat it as terminal only by falling out of the `QUEUED/RUNNING` check |
| retry on network error | implicit, unbounded | `keepPolling` is initialised `true` (`:30`) and only set `false` on a successful terminal read → every failure retries in 2 s forever |
| retry on 4xx/5xx | **wrong** | `fetchResearchStatus` throws on `!response.ok` (`research.client.ts:12-14`) → 404/500 also retries forever |
| user-visible error | no | `console.error` only (`:48`) |
| user-initiated retry | no | — |
| backoff / attempt cap | no | fixed 2 s, unlimited attempts |
| abort on unmount | **yes, correct** | `AbortController` (`:26`), `signal.aborted` guards (`:38`, `:44`, `:51`), `clearTimeout` (`:61-63`), passed into `fetch` (`research.client.ts:9`) |
| empty state | n/a on detail page | missing on the list page (§2.3) |

Server side (read-only observation): `ResearchService.runResearch` is an in-process
fire-and-forget (`research.service.ts:60-62`), `status: 'INTERRUPTED'` is never written
anywhere in `apps/api/src`, and `lastHeartbeatAt` is never updated. A run interrupted by an
API restart therefore stays `RUNNING` in the database **and** in the UI polls forever.

`research.client.ts:16`). Only the `POST /research` response is validated

| Field | API (`prisma/schema.prisma:36-50`) | Web type | Aligned? |
| --- | --- | --- | --- |
| `id` | `String` (cuid) | `string` | yes |
| `productId` | `String` | `string` | yes |
| `country` | `String` | `string` | yes |
| `status` | `ResearchStatus` (5 values) | union of the same 5 | yes (2 values unused) |
| `stage` | `String?` | `null \| string` | yes |
| `result` | `Json?` | `null \| string` | **latent mismatch** — today stage 02 returns the literal `'completed'` (`company-discovery.service.ts:59`), so a string happens to be correct; any object result breaks the type silently |
| `error` | `String?` | `null \| string` | yes |

| `GET /products` → `possibleSearchTerms` | `String[]` | omitted from web `Product` | drift (unused field) |

No shared source of truth exists between `apps/api` DTOs and `apps/web` types; every
contract is mirrored by hand on both sides.

### 1.6 Tailwind / PostCSS — enabled, but two systems in parallel

Facts:

- Tailwind **v4.3.5** + `@tailwindcss/postcss` v4 in `devDependencies`
  (`package.json:18,22`); no `tailwind.config.*` (correct for v4).
- `postcss.config.mjs:1-5` registers only `@tailwindcss/postcss` — consistent.
- `app/globals.css:1` `@import 'tailwindcss';`, imported once by `app/layout.tsx:3`.
- `@theme inline` (`globals.css:5-13`) maps the app palette to semantic utilities
  (`bg-surface`, `text-muted`, `border-border`, `text-ok`, `text-error`).
- **Zero usages** of those semantic utilities anywhere. The only Tailwind utilities in the
  codebase are `flex`, `flex flex-col gap-2`, `flex gap-2` in
  `_pages/research/ui/research-progress.tsx:68-69` and `researches-page.tsx:11`.
- Everything else is hand-written CSS (`globals.css:63-301`: `.card`, `.button`,
  `.status`, `.muted`, `.form`, `.field`, …) plus 6 inline `style={{…}}` props
  (`app/page.tsx:15`, `app/health/page.tsx:86`, `app/products/page.tsx:76,102`,
  `app/products/[id]/page.tsx:63`, `research-progress.tsx:72`).
- The pipeline does work, including for the `_pages` folder: the production stylesheet
  (`apps/web/.next/static/chunks/2gx0_hsupte32.css`, rebuilt during this audit) contains
  `.flex{`, `.gap-2{`, `.flex-col{`, so v4 automatic source detection scans `_pages`.
- **Cascade-layer trap:** in the built CSS, `@layer utilities` starts at character offset
  4138, while every hand-written rule (`.card` 4828, `.muted` 5136, `p{margin` 4794,
  `main{` 4701, `:root{` 4348) is emitted **after** the layers and is therefore
  **unlayered**. Unlayered declarations beat every `@layer` utility regardless of
  specificity, so e.g.
  `<p className="mt-0">` cannot override `p { margin: 0 0 1rem }` (`globals.css:55-57`).
  Today this is harmless because the utilities used are for layout only, but it will bite
  as soon as Tailwind is used for spacing/typography on elements that `globals.css` styles.
- Consequence for consistency: the two new pages look different from the product pages —
  no `.card`, no `.page-header`, no `.muted`, no breadcrumb — because they ignore the
  existing class vocabulary.

### 1.7 Build and typecheck constraints

Reproduced during this audit:

```text
node node_modules/typescript/bin/tsc -p apps/api/tsconfig.json --noEmit
  → exit 0

node node_modules/typescript/bin/tsc -p apps/web/tsconfig.json --noEmit --incremental false
  → exit 0   (with .next/types present)

# cwd apps/web
node ..\..\node_modules\next\dist\bin\next build
  → "Compiled successfully in 2.7s"
  → "Running TypeScript ..."
  → spawn EPERM
  → exit 1
```

Facts:

- `next build` **cannot complete in the DSH sandbox**: it compiles, then dies spawning its
  TypeScript worker (`spawn EPERM`). This confirms `HANDOVER.md:38-40`. The production
  bundle, prerender output and route-type build validation are therefore never produced
  here; run the build in a normal terminal.
- `npx next build` fails even earlier in this sandbox (PowerShell named-pipe denial), so use
  the direct `node .../next/dist/bin/next` form or a real shell.
- The root `npm run build` also runs `prisma generate` + `tsc` for the API first, so a web
  build attempt in this sandbox always ends in the same `spawn EPERM`.
- The web `tsconfig.json` has `incremental: true` with `noEmit`; plain
  `tsc -p apps/web/tsconfig.json` writes `tsconfig.tsbuildinfo` (git-ignored). Add
  `--incremental false` for a pure check.
- `apps/web/tsconfig.json:31-37` includes `.next/types/**/*.ts`. Because the failed build
  still generated `.next/types/routes.d.ts`, `tsc` did validate route params and passed.
  **If `.next/` is absent the include silently matches nothing** and route validation is
  skipped — `tsc` is not a substitute for a real build.
- There is **no** `typecheck`, `lint`, `test` or `format` script in any `package.json`, no
  ESLint config, no Prettier config, no test runner and no `*.test.*`/`*.spec.*` files.
- `next.config.ts` is empty (`{}`): no rewrites, no redirects, no `basePath`.
- Only `next-env.d.ts` is generated; `apps/web/AGENTS.md` holds the Next.js agent-rules
  block that `next dev` re-adds.

## 2. Problems by priority

### P0 — the feature cannot deliver its value

**2.1 Result and error are never rendered.**
`entities/research/model/types.ts:19-20` fetches `result` and `error`; no component reads
them (`research-page.tsx:8-19`, `research-progress.tsx:67-86`). A `COMPLETED` run looks
exactly like a stuck one, and the output of stage 02 is unreachable from the UI.
*Fix size:* small (one state block + a `<pre>` for the JSON).

**2.2 Polling cannot fail gracefully; it fails silently and forever.**
Fixed 2 s interval with no attempt cap or backoff (`research-progress.tsx:52`), errors
swallowed to console (`:45-49`), `keepPolling` stays `true` on every exception (`:30`), and
404/500 are thrown
the same way as a network blip (`research.client.ts:12-14`). Combined with an API that never
writes `INTERRUPTED` and never updates `lastHeartbeatAt`, an interrupted run means an
infinite request loop and a permanent spinner.

**2.3 The job list is orphaned and has no states.**
No link to `/researches` exists (§1.5.4). `researches-page.tsx:10-15` renders rows only:
no empty state, no error state, no `.card`, raw cuid as the link label, no product name, no
date. `fetchResearches` throws (`research.server.ts:23-26`) and there is no `error.tsx`, so
an API outage produces Next's default error page instead of the app's `.status.error` card.

### P1 — correctness and contract drift

**2.4 Hardcoded seven-country list contradicts the project rules.**
`lib/countries.ts:1-9` hardcodes `LT, LV, EE, HU, ES, DE, PL` and sends the English country
*name* as `country`. `AGENTS.md` says the market can be any country and explicitly forbids a
fixed country list. `i18n-iso-countries` is already an API dependency (`apps/api/package.json:25`).

**2.5 Dead success branch in the research form.**
`research-form.tsx:49-53` + `actions.ts:8-12`: unreachable code that documents behaviour the
action does not have (it redirects). A future dev will "fix" the wrong layer.

**2.6 Contract is unvalidated and mirrored by hand.**
`research.server.ts:14,27` and `research.client.ts:16` return `response.json()` unchecked;
`result` is typed `string` over a `Json?` column. Any stage-02 shape change becomes a
runtime surprise instead of a compile error. The same pattern exists for `Product`
(`lib/products.ts:37`, `app/products/page.tsx:35`).

**2.7 Stale server-rendered status after completion.**
`research-page.tsx:14-17` renders `status`/`stage` from the server render; the poller
updates only its own copy and never calls `router.refresh()` (no `useRouter` in the codebase).
After a run finishes, the page shows a stale `RUNNING` line above a fresh `COMPLETED` line,
and a non-null stage that the API has already set to `null` (`research.service.ts:125`).

**2.8 State is not keyed by `jobId`.**
`useState(initialResearch)` (`research-progress.tsx:15`) is initialised on mount only.
Navigating from `/researches/A` to `/researches/B` reuses the component and shows A's data
until the first poll resolves (and the effect's dependency on `initialResearch.status` does
not help, because props do not change).

**2.9 Three different error-handling conventions.**
Products: `{ok:false,error}` unions (`lib/products.ts:11-13`). Product forms: parse the Nest
`message` payload (`app/products/actions.ts:52-64`). Research: throw generic
`Error('… HTTP n')` (`research.server.ts:10-12`) and drop the API's message
(`app/products/[id]/actions.ts:46-51`). Same API, three behaviours, three UX outcomes.

**2.10 Duplicated product validation.**
The 200/2000-character rules exist twice (`app/products/actions.ts:25-37`,
`app/products/[id]/edit/actions.ts:26-37`) and a third time in the API DTOs. It will drift.

**2.11 Accessibility of the progress UI.**
No `aria-live`/`role="status"` anywhere in `apps/web`, so status changes are silent to
screen readers; the spinner glyph is `aria-hidden` (`:70-80`) but is the only thing that
moves; the raw `stage` string is user-visible implementation text.

### P2 — maintainability

**2.12 Two styling systems and a cascade-layer trap.** §1.6. New pages do not use the
existing class vocabulary; semantic theme tokens are defined and unused; unlayered globals
override utilities.

**2.13 No lint/format gate; two code styles.** `app/` and `lib/` have **no semicolons**
(`app/products/page.tsx`, `lib/products.ts`), while `entities/` and `_pages/` use
semicolons (`entities/research/model/types.ts`, `research-progress.tsx`). `app/researches/page.tsx`
uses double quotes and is not indented (`:10-12`); `research-form.tsx:27` is mis-indented
with two stray blank lines at `:47-48`. With 1466 lines total this is cheap to normalise now.

**2.14 FSD drift.** `lib/` mixes three responsibilities (`shared/api`, a product entity API,
shared data), server actions and forms live inside route folders, and
`app/products/page.tsx` contains a data fetch that belongs to an entity. See §4.

**2.15 Route handler is fragile.** `app/api/research/[jobId]/route.ts:9-20`: no `try/catch`,
no timeout, no `jobId` validation, blindly relabels any upstream body as
`Content-Type: application/json` — a dead API yields an HTML 500 to a JSON client.

**2.16 List endpoint is unordered and unbounded.** `ResearchService.getAll()` uses
`findMany()` with no `orderBy`/`take` (`research.service.ts:79-82`), unlike products
(`products.service.ts:22-24`), so the list order is undefined and grows without limit.

**2.17 Stale docs.** `README.md:114-117` still describes research as synchronous
(`{ "status": "completed" }`, possible search terms), and its layout tree (`:32-42`) omits
`researches`, `_pages`, `entities` and the polling proxy.

### P3 — polish

- `notFound()` (`app/products/[id]/page.tsx:24`) falls back to the unstyled default 404; no
  `app/not-found.tsx`.
- Next 16 idiom: pages hand-write `params: Promise<{id: string}>` instead of
  `PageProps<'/products/[id]'>` (generated in `.next/types/routes.d.ts`). Both typecheck.
- `frames` array is re-created on every render and the spinner keeps spinning after a
  terminal state (`research-progress.tsx:14,79`).
- `export const dynamic = 'force-dynamic'` repeated on 6 pages while every fetch already
  uses `cache: 'no-store'`.
- `productId={id}` is passed from the raw route param instead of `product.id`
  (`app/products/[id]/page.tsx:71`).
- `_pages/research/index.ts:2` typo `ResearchProgres`; file/export names disagree
  (`research-progress.tsx` → `ResearchProgressProps`).

## 3. Small refactor steps

Ordered so each step is one small commit, typechecks on its own, and changes no behaviour
until the step that is supposed to change it. `tsc` after each step.

1. **`shared/api` extraction (no behaviour change).** Move `lib/api.ts` to
   `shared/config/env.ts` exporting `apiUrl` (server-only) and add
   `shared/api/http.ts` with `getJson`/`postJson`: base URL, `cache: 'no-store'`, timeout,
   `{ok,data} | {ok:false,status,error}`. Port `lib/products.ts` and
   `entities/research/api/*.server.ts` onto it.
2. **Contract schemas.** Add `entities/research/model/schema.ts` with
   `researchResponseSchema = z.object({...})` and `z.infer` the type from it; parse in the
   server/client API functions and return a typed failure instead of throwing raw. Do the
   same for `Product` and delete the duplicate type in `app/products/page.tsx:12-18`.
   Decide `result` explicitly (`z.unknown()` today) instead of `string`.
3. **Kill dead code.** Remove the `'success'` branch and `jobId` from
   `ResearchFormState`/`research-form.tsx`; fix the `ResearchProgres` export (or drop the
   barrel); drop unused exports from `entities/research/index.ts`.
4. **Render terminal states.** In `research-progress`: stop the spinner, render `error`
   when `FAILED`, render `result` (collapsible `<pre>`) when `COMPLETED`, add
   `role="status"`/`aria-live="polite"`, add a "start another run" link. Single source of
   truth for status — remove the duplicate lines in `research-page.tsx:16-17`.
5. **Fix polling.** Terminal detection by "not `QUEUED`/`RUNNING`"; do not retry on
   4xx (404 → stop + message); exponential backoff with a cap for transient errors; show the
   error; call `router.refresh()` on a terminal transition; `key={jobId}` on the client
   component (or `useState`+effect reset) so navigation cannot show stale data.
6. **Reachability and list states.** Add `/researches` to `app/page.tsx` links and to
   `products/[id]`; add breadcrumbs to both research pages; add empty state, error state and
   `card` markup to `researches-page.tsx`; show `productId`/`country`/`createdAt` and sort
   newest-first (API `orderBy`, or sort in the page as an interim).
7. **Countries.** Replace `lib/countries.ts` with a shared dataset (reuse
   `i18n-iso-countries` or one file generated once) and keep `{code,name}`; decide whether
   the API should receive the code instead of the name before changing the payload.
8. **App-level boundaries.** Add `app/error.tsx` (client, uses `.status.error` + retry),
   `app/not-found.tsx`, `app/loading.tsx`.
9. **Harden the proxy.** `try/catch` around the upstream fetch, an `AbortSignal.timeout`,
   pass through the upstream `content-type`, return a JSON body on upstream failure.
10. **CSS layering.** Wrap the hand-written block of `globals.css` in
    `@layer components` (or split `globals.css` into `@layer base` + `@layer components`) so
    Tailwind utilities can win again; then migrate `_pages/research*` to `.card`,
    `.page-header`, `.muted` and delete the inline styles.
11. **Tooling gate.** Add Prettier + a flat ESLint config + `typecheck`/`lint`/`format`
    scripts in `apps/web`; run `format` once over `apps/web` to end the semicolon split.
12. **FSD moves** (§4) only after 1–11 — pure file moves, no logic.

Do **not** start with step 12: moving files first multiplies the diff of every later step.

## 4. Architecture: Lite FSD

**Recommendation: yes, Lite FSD — but folder names are the cheap part.** The current
structure already implements the two most error-prone ideas (`entities/*/api` with
`.server.ts`/`.client.ts`, `_pages` as a non-routable pages layer). What is missing is
enforcement and a contract boundary. For a project that will grow, the single
highest-value change is a **shared contract source** (step 2 above / §4.3), not more layers.

### 4.1 Target tree

```text
apps/web/
├── app/                          # routing only: metadata, params, render a view
│   ├── api/research/[jobId]/route.ts
│   ├── products/{page.tsx,new/page.tsx,[id]/page.tsx,[id]/edit/page.tsx}
│   ├── researches/{page.tsx,[jobId]/page.tsx}
│   ├── error.tsx  not-found.tsx  loading.tsx
│   ├── layout.tsx  globals.css
├── _pages/                       # FSD pages layer (underscore = not routable)
│   ├── products/                 # list + detail + edit views
│   └── researches/               # list + detail views
├── features/                     # user actions only
```

### 4.2 Rules worth enforcing (the actual value)

1. Imports flow **down only**: `app` → `_pages` → `features` → `entities` → `shared`.
   No upward imports, no sideway imports between sibling features.
2. One public `index.ts` per slice; cross-slice imports go through it, never
   `.../ui/internal-thing`.
3. `app/**` contains **no** data fetching, no forms, no business logic — only metadata,
   param validation and the view component. This is what makes routes swappable.
4. Server actions live in `features/*/api`, next to the form that calls them, not in the
   route folder.
5. `*.server.ts` may import `API_URL`; `*.client.ts` must not. Client code only talks to
   same-origin `/api/*` (today that is the proxy — correct, since the API has no CORS).
6. Types are `z.infer` of a schema in `model/schema.ts`. No hand-written mirror types, no
   unvalidated `response.json()`.
7. Read-only pages get a `_pages` slice + entity query; **`features` is only for verbs**
   (create, edit, start, poll). This is the "Lite" part: no `processes` layer, no
   per-segment over-splitting, `ui/api/model` only where it earns its place.

**Next.js specifics**

- Keep `app/` as the router and `_pages/` as the FSD pages layer. A top-level `pages/`
  directory is reserved for the Pages Router and would be picked up as routes; the
  underscore keeps it private (`node_modules/next/dist/docs/01-app/01-getting-started/02-project-structure.md`,
  "Private folders").
- Moving layers between root folders does not need Tailwind config work: v4 detects sources
  automatically and already scans `_pages` (proven by the built CSS, §1.6). Verify the built
  CSS once after the move.
- If layers move under `src/`, update the `@/*` path alias and the `tsconfig` include — the
  move buys tidiness but costs churn; not required by Lite FSD.

### 4.3 What I would do *instead of* (or before) deeper FSD

Extract the API contract into one workspace package, e.g. `packages/contracts`:

- `research.schema.ts`, `product.schema.ts` — zod schemas plus `z.infer` types.
- API side: derive the DTO validation from the same schemas (or at minimum assert
  `CreateResearchDto` ↔ schema in a test) instead of `class-validator` + hand mirrors.
- Web side: parse every response with those schemas; `tsc` then fails on drift instead of
  production.
- Later, if the API gets external consumers, switch to `@nestjs/swagger` + generated client;
  that is heavier and premature while `apps/web` is the only client.

This directly removes the §2.6 class of bugs, which is the recurring cost in this codebase.
Lite FSD alone does not solve it — layers and contract drift are orthogonal.

**Alternative considered:** Next.js-native colocation (everything under `app/`, no layers).
It is simpler for 29 files, but with a "fairly large" project ahead it puts route folders and
business logic in one place, which is exactly what `products/[id]/actions.ts` +
`research-form.tsx` already shows the cost of. Keep FSD.
